# 计费机制定案：根因、架构分叉与完整结论

日期：2026-08-06
作者：Kael（经三轮对抗性校验）
状态：待 Kari 决策架构方向

---

## 1. 根因（最终版，经三轮校验修正）

**根因一（迁移）：计费层被「改名迁移」而非「重新推导迁移」。**
yunwu → OpenLux 切换时，计费语义常量被当可移植字段改名保留：`yunwuGroupRatio 6 → mapping.groupRatio`、`supplierCreditToRmb 0.5`、除数 500000（NewAPI 默认假设）、「1 积分=¥0.5」。这些未经验证的假设成为整轮债务源头。

**根因二（结构）：插件在为一个「不可完全观测、动态变化、第三方控制」的定价系统做逐次预测。**
真实扣费 = f(模型定价配置, 动态渠道路由, 分组倍率, 站点 QuotaPerUnit, 特殊计费路径)。插件用「目录快照 + 公式」复刻，但目录不完备（MJ off-table）、公式语义可被站点颠覆（除数 5000）、路由结果只部分可观测（同步有头/MJ 无头）、日志精确通道关闭。

**根因三（验证缺失）：没有闭环反馈。**
预测错了（表值失效、供应商调价、渠道故障路由）没有任何自动机制发现——只靠人发现（本次就是靠人工对账才发现除数/汇率/off-table）。

## 2. 痛点全集

1. 供应商定价黑盒且动态（目录不完备、路由随机、配置随时可改）
2. 观测手段残缺（响应头仅同步；日志 API 关闭；余额位移有滞后/并发污染；观测枚举未穷尽）
3. 插件被迫当预言机（预扣防亏损 + 结算防多收，都无法验证）
4. **可持续性**：正确性依赖人工周期性维护（重探测/盯告警），无自维护机制

## 3. 硬约束（不可消除）

- 无日志通道 → 逐次真实扣费不可精确获取
- 动态路由 → 逐次成本在生成前未知、生成后对无头模型仍未知
- 供应商可随时调价 → 任何静态校准都会漂移

## 4. 架构分叉

### A. 加固版 cost-plus（逐次精确 + 边界兜底）
- 预扣 = 真上界（主 key usable_group 全表 max × 自适应 margin / off-table 探测分布 max）
- 结算 = 实际路由优先（sync 头×表值；无头按探测 max，政策 a）
- 探测 = 分布校准（N 采样、off-table 检测、专用 key 强制）
- **对抗性校验确认的残留**：6h 表陈旧窗口；探测 key≠主 key 路由宇宙；margin 自适应信号未定义；政策 a 是「有界风险」非零风险；渠道故障超 margin 仍亏；同步 off-table 未探测会静默亏损（需门禁全模型）
- 优点：逐用户公平（付实际成本）；缺点：复杂、失效面大、仍靠人工校准

### B. 固定定价（消除逐次预测）
- 用户按模型付固定价（产品定价，含 margin）；结算 = 固定价 × 张数，无任何公式
- 预扣 = 固定价（简单）；探测 = 仅用于一次性定价校准（不用于结算）
- **闭环反馈在「可观测」的聚合层**：月利润率 = 收入（用户消耗积分）− 供应商余额位移（两者都可免费只读观测）→ 低于阈值自动告警/调价
- **对抗性校验**：风险从「逐次」移到「周期」——单次生成可能大幅亏损（gpt 价差 47 倍），但聚合层可监控、可调价、可 cron 自动化；定价仍需按最坏情况校准一次（观测限制仍在，但容错大得多）；便宜用户补贴贵用户（公平性为产品决策）
- 优点：从根上消除逐次预测、代码面大幅缩小、失效面小、可持续（监控可自动化）；缺点：逐用户不公平、定价保守则用户偏贵

## 5. 共同必需件（无论 A/B）：聚合利润率监控

无日志通道后，**唯一可靠的补偿控制是聚合层闭环**：
- 输入：用户消耗积分（users.v2.json + ledger）+ 供应商余额位移（total_usage delta，免费只读）+ usdToRmb
- 输出：周期利润率（月/周）→ 低于阈值告警 → 人工或自动调价
- 可 cron 自动化 → 直接解决痛点 4（可持续性）
- 试用/管理员免费消耗须单列（作为营销成本计入）

## 6. 建议

**推荐 B（固定定价 + 聚合监控）**，理由：
1. 直接消除根因二（逐次预测），而不是加固在它周围
2. 反馈闭环建立在「可观测」的聚合层（余额+收入都可免费读）
3. 复杂度与失效面数量级下降（结算=固定价，无除数/汇率/off-table/污染在结算路径）
4. 可持续（监控 cron 化）

**若 Kari 坚持逐用户按实际成本计费（公平性优先）→ 选 A**，必须同时补 6 个洞 + 聚合监控作为补偿控制。

## 7. 决策点

1. 架构方向：A（cost-plus 精确）还是 B（固定定价）？
2. 若 B：固定价按「模型 × 张数」还是「模型 × 档位（按 prompt 长度/尺寸）」？初始价格如何定（按探测分布 max×margin？）
3. 若 B：用户已购积分余额如何处理（价格体系变更，积分购买力变化）？
4. 聚合监控周期与告警阈值（建议：周报 + 月利润率 < 预设线告警）

## 8. 实施影响

- A：继续三层机制 + 6 洞修补 + 监控（改动大）
- B：结算改固定价表（删除/旁路动态结算）、预扣改固定价、探测降级为定价校准工具、新增聚合监控 cron（改动中等，净简化）
- 无论哪种：聚合监控先做（低风险、高价值、两者必需）
